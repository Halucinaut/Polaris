## Polaris M2 Todo：0.6B Math DPO

> **2026-08-31 收口状态**：M2 已完成“工程与诊断通过，效果目标未通过”的验收。DPO v1 证明训练链路，v2–v4 style experiments 与自由生成分支点归因证明当前设置无法稳定迁移目标模板。停止新的 DPO 效果实验，进入 M2.5 RL sanity 准备。正式结论、run 对照和归因边界见 `docs/experiment_notes/m2_dpo_closeout.md`；下文保留为原始计划、验收标准和历史记录。

1. M2 定位

M2 是 Polaris 从 SFT 进入 preference optimization 的第一阶段。M1 已在 Qwen3-0.6B 上完成 GSM8K Math SFT，证明本地训练链路、格式协议、baseline eval、SFT 数据构造、LoRA 训练、sample diff、run registry 和 run_report 可以形成最小闭环。

M2 的目标是在 M1 SFT checkpoint 基础上完成第一组可复现 Math DPO。M2 不追求数学能力大幅提升，核心学习目标是理解 DPO 的训练信号、数据构造、logprob 计算、preference margin、length bias、模式坍缩和 SFT→DPO 的实验诊断方法。

M2 的完成结果需要回答三个问题：

1. 我们能否构造一批方向明确、噪声可控的 chosen/rejected pairs？
2. 我们能否正确实现或接入 DPO loss，并验证 logprob、loss mask、margin 方向正确？
3. DPO 之后模型行为相对 SFT 发生了什么变化：更正确、更规范、更短、更模板化，还是出现退化？

M2 通过后进入 M2.5。M2.5 的目标是 RL sanity，即验证 rollout、reward、logprob、KL、checkpoint、resume 和日志链路。M2 不直接进入 GRPO/PPO；M2 必须先证明 preference optimization 的数据、训练和诊断能力已经具备。

2. 从 M1 到 M2 的承接关系

M1 的产物是 M2 的输入。

M1 提供了三个关键基础：

第一，SFT checkpoint。M2 的 DPO policy 应从 M1 的有效 SFT checkpoint 初始化。DPO 是在已经具备目标格式和基础任务行为的 policy 上做偏好优化，不应从 base model 重新开始。

第二，统一格式协议。M1 已确认训练、推理、评估必须使用一致的 system prompt、chat template、target 格式和 eval checker。M2 的 chosen/rejected 必须沿用 M1 的格式口径，避免把 prompt 不一致误判成 DPO 效果。

第三，评估工具链。M1 已有 eval_math / eval_gsm8k、baseline vs SFT 对比、sample diff、hardware log、run registry。M2 应复用这些工具，并新增 DPO 专属指标：chosen_logprob、rejected_logprob、logprob_margin、preference_accuracy、length gap、KL proxy。

M2 不重新定义 Math 任务，不重新选择大数据集，不切换模型规模，不引入 Tool-call。M2 只在 Qwen3-0.6B + GSM8K + M1 SFT checkpoint 上验证 DPO。

3. M2 不做事项

M2 阶段禁止扩展以下内容：

* 不做 GRPO、PPO、OPD。
* 不做 Tool-call。
* 不做多数据集混合。
* 不做 4B/8B 训练。
* 不追求 benchmark SOTA。
* 不用云端训练替代本地闭环。
* 不把失败 run 手工改成 completed。
* 不用未经审查的 synthetic pair 直接训练。
* 不只看 loss 下降判断 DPO 成功。
* 不把 DPO 后 pass@1 小样本波动写成泛化能力结论。

5. M2 执行主线

5.1 固定 pair 协议

M2 第一件事是定义 chosen/rejected pair 的构造协议。DPO 的训练信号来自相对偏好，不来自单条标准答案。pair 协议决定模型会学到什么。

需要完成：

docs/format_notes/dpo_math_pair_protocol.md

该文档至少包含：

* pair 的基本定义。
* chosen 的合格标准。
* rejected 的合格标准。
* 允许的 pair_type。
* 禁止进入训练的数据类型。
* 长度偏差控制规则。
* 格式偏差控制规则。
* 人工审阅标准。
* M2 是否允许 format-only pair。
* M2 是否优先 answer-correctness pair。
* pair 构造与 M1 SFT 格式协议的关系。

推荐 pair_type：

gold_vs_wrong_model_output
correct_boxed_vs_wrong_boxed
correct_formatted_vs_unformatted_correct
sft_correct_vs_baseline_wrong
sft_improved_vs_sft_regressed

M2 第一版应优先使用 answer-correctness pair。format-only pair 可以保留少量用于维持格式，但不能成为主导数据，否则 DPO 可能继续强化格式而非数学正确性。

禁止样本：

chosen 和 rejected 内容几乎相同
chosen 和 rejected 只有长度差异
chosen 与 rejected 都答案错误
chosen 与 rejected 都答案正确且解释质量无法区分
rejected 为空输出
rejected 是截断导致的残缺文本
chosen 极长而 rejected 极短
pair 方向需要主观猜测

人工任务：亲自审阅至少 20 组候选 pair，并标注 clean、weak、length-biased、format-only、invalid。该动作不能完全交给 LLM。

5.2 构造 DPO 数据集

在 pair 协议确定后，编写或完善：

scripts/prepare_dpo_data.py

输出：

data/math/splits/dpo_v1.jsonl
data/math/reports/dpo_v1_report.json

dpo_v1.jsonl 推荐 schema：

{
  "id": "dpo_000001",
  "messages": [
    {"role": "system", "content": "..."},
    {"role": "user", "content": "..."}
  ],
  "chosen": "<think>\n...\n</think>\n\\boxed{...}",
  "rejected": "<think>\n...\n</think>\n\\boxed{...}",
  "answer": "...",
  "source": "gsm8k",
  "pair_type": "gold_vs_wrong_model_output",
  "quality_tag": "clean",
  "metadata": {
    "chosen_answer_correct": true,
    "rejected_answer_correct": false,
    "chosen_format_adherence": true,
    "rejected_format_adherence": true,
    "chosen_length": 0,
    "rejected_length": 0,
    "length_ratio": 0.0
  }
}

dpo_v1_report.json 至少统计：

total_pairs
kept_pairs
filtered_pairs
pair_type_distribution
quality_tag_distribution
chosen_avg_length
rejected_avg_length
avg_length_gap
avg_length_ratio
chosen_format_adherence
rejected_format_adherence
chosen_answer_correct_rate
rejected_answer_correct_rate
duplicate_prompt_count
same_answer_pair_count
extreme_length_gap_count

合格标准：

dpo_v1.jsonl 至少包含 200–500 组 pairs。
clean 或 high_confidence pair 占主要比例。
chosen_answer_correct_rate 明显高于 rejected_answer_correct_rate。
chosen/rejected 平均长度差不能成为唯一偏好信号。
空输出、同答案弱偏好、极端长度差样本被过滤。
人工抽查 30 组，pair 方向错误率不能高。

如果最终只能构造少量高质量 pair，也可以先跑小规模 DPO sanity，但不能宣称完成完整 M2。

5.3 实现 DPO 训练链路

DPO 训练脚本为：

scripts/train_dpo.py

配置文件为：

configs/qwen3_0_6b/dpo_math.yaml

训练初始化应基于 M1 SFT checkpoint。reference model 可以使用冻结的 SFT checkpoint 或 base checkpoint，第一版建议明确写入 config，避免后续无法复现。

DPO 训练至少记录以下指标：

dpo_loss
chosen_logprob
rejected_logprob
logprob_margin
preference_accuracy
chosen_length
rejected_length
completion_length
learning_rate
tokens_per_sec
peak_memory

如果实现 KL proxy，也记录：

policy_ref_logprob_gap
chosen_policy_ref_gap
rejected_policy_ref_gap

10-step sanity 必须先于完整 DPO。sanity 目标是验证链路，不是验证效果。

必须生成：

debug_dpo_batch.json

debug 文件至少包含：

prompt_text
chosen_text
rejected_text
chosen_token_ids
rejected_token_ids
chosen_loss_mask_summary
rejected_loss_mask_summary
chosen_response_logprob
rejected_response_logprob
logprob_margin
truncated

重点检查项：

logprob 是否只覆盖 assistant response。
prompt token 是否被排除在 loss/logprob 之外。
chosen/rejected 是否使用同一个 prompt。
chosen/rejected 是否套用了相同 chat template。
reference model 是否冻结。
policy model 是否加载了 M1 SFT checkpoint。
margin 方向是否为 chosen - rejected。

合格标准：

10-step DPO sanity completed，或 failed 且有明确 failure note。
debug_dpo_batch.json 能解释 prompt、chosen、rejected、mask、logprob。
chosen/rejected logprob 方向可解释。
train_metrics.jsonl 能记录 DPO 专属指标。
run_meta.yaml 状态正确，不手工改 completed。

5.4 跑完整 DPO run

完整 DPO run 的目标是观察 preference optimization 是否按预期改变模型行为。

正式 run 必须通过 registry 创建。完整训练过程中记录 metrics、hardware、checkpoint 和 sample output。

训练中重点观察：

dpo_loss 是否下降
logprob_margin 是否上升
preference_accuracy 是否高于随机水平
completion length 是否异常变短或变长
format_adherence 是否保持
是否出现模板化输出
是否出现只输出 boxed answer 而弱化 reasoning

合格标准：

至少一组完整 DPO run completed。
训练过程无 NaN/Inf。
logprob_margin 相比初始阶段有上升趋势。
preference_accuracy 高于 0.5，且不能只由长度差解释。
completion length 没有异常坍缩。
format_adherence 不低于 SFT。
checkpoint 可以加载并完成 eval。

如果 DPO run 完成但 eval 退化，M2 可以标记为 partial pass 或 failure pass，前提是 failure analysis 清楚解释原因。Polaris 允许失败 run，但不允许缺少诊断。

5.5 DPO 后评估

DPO 完整 run 后，必须在同一测试集上比较：

baseline
SFT
DPO

至少记录：

pass_at_1
answer_extraction_success
format_adherence
avg_completion_length
invalid_output_rate

M2 评估应尽量沿用 M1 的 test set 和 system prompt，避免 prompt 不一致导致误判。M1 已暴露过 eval system prompt 不一致问题，M2 必须显式检查。

合格标准：

DPO 的 format_adherence 不低于 SFT。
DPO 的 answer_extraction_success 不低于或基本不低于 SFT。
DPO 的 pass_at_1 不明显低于 SFT。
如果 pass_at_1 下降超过 5%，必须写 failure analysis。
avg_completion_length 没有异常缩短或膨胀。

DPO 后 pass@1 小幅提升可以记录为观察结果，不能写成稳定结论，除非测试集规模足够大且有重复实验。

5.6 样例审阅

M2 必须人工审阅至少 20 条 SFT vs DPO sample diff。该任务必须由用户亲自完成，LLM 只能辅助生成表格、解释分类边界和汇总结果。

分类标签建议：

improved
regressed
over-formatted
length-biased
mode-collapsed
unchanged
invalid

审阅时至少检查：

答案是否变正确
推理是否更清楚
输出是否更短但丢失推理
是否过度模板化
是否只强化 boxed 格式
是否产生固定句式
是否把正确 SFT 输出改坏

合格标准：

至少 20 条样例被人工分类。
每类至少有简短说明或代表样例。
sample diff 结果进入 run_report。
M2 结论不能只依赖 aggregate metrics。

6. M2 最低通过标准

M2 通过必须同时满足以下条件：

1. dpo_math_pair_protocol.md 完成，pair 构造原则明确。
2. dpo_v1.jsonl 可复现生成，且有 dpo_v1_report.json。
3. 至少人工审阅 20 组候选 pair。
4. 10-step DPO sanity 通过，或失败但有完整 failure note。
5. debug_dpo_batch.json 能检查 prompt、chosen、rejected、mask、logprob。
6. 至少一组完整 DPO run completed。
7. logprob_margin 方向正确，且训练中有上升趋势。
8. preference_accuracy 高于随机水平，且不能只由长度差解释。
9. DPO 后 format_adherence 不低于 SFT。
10. DPO 后 pass_at_1 或 answer_extraction_success 不明显退化。
11. 至少人工审阅 20 条 SFT vs DPO sample diff 并分类。
12. run_report 明确说明是否进入 M2.5。

如果第 6 条无法满足，即没有完整 DPO run completed，M2 不通过。可以进入 debug 周，但不能进入 M2.5。

如果完整 DPO run completed，但指标退化，只要 failure analysis 清楚、样例审阅充分、DPO loss 和 logprob 诊断可信，M2 可以记为“工程通过，效果未通过”。是否进入 M2.5 取决于退化原因是否已定位。

7. M2 进入 M2.5 的条件

M2.5 是 RL sanity，不是效果优化阶段。进入 M2.5 前，M2 必须证明以下能力：

preference data 构造能力
chosen/rejected logprob 计算能力
response-only loss mask 检查能力
policy/reference 对照意识
训练指标与样例审阅结合的诊断能力
run registry 记录真实偏好训练的能力

允许进入 M2.5 的条件：

DPO 训练链路稳定。
DPO debug 信息足以排查 mask/logprob 错误。
M2 run_report 明确记录 DPO 的有效点和失败点。
没有未解释的严重格式退化。
没有未解释的严重 mode collapse。
用户已亲自审阅 pair 和 sample diff。

不允许进入 M2.5 的情况：

DPO loss 实现未经验证。
logprob 覆盖 prompt 和 response 的边界不清。
pair 质量没有人工审阅。
run completed 但无 debug dump。
DPO 后输出严重坍缩且原因未知。
SFT checkpoint、reference model、policy model 来源混乱。

9. 用户必须亲自完成的任务

M2 中以下任务不能完全交给 LLM：

1. 判断 pair 是否有真实偏好价值。
2. 人工审阅至少 20 组候选 pair。
3. 解释 DPO loss 中 policy、reference、chosen、rejected 的关系。
4. 检查 debug_dpo_batch.json，确认 logprob 和 mask 边界。
5. 人工审阅至少 20 条 SFT vs DPO sample diff。
6. 判断 DPO 是否存在 length bias 或 mode collapse。
7. 写出 M2 是否进入 M2.5 的第一版结论。

LLM 可以辅助写脚本、生成报告模板、整理指标、检查实现风险、压缩 run_report，但不能替代上述学习动作。

10. M2 完成定义

M2 完成时，应能用一句话概括：

在 Qwen3-0.6B 的 M1 SFT checkpoint 基础上，Polaris 完成了第一组 Math DPO，构造并审查了 chosen/rejected pairs，验证了 response-only logprob 与 DPO loss，记录了 margin 和 preference accuracy，完成了 baseline/SFT/DPO 对比和样例审阅，并据此判断是否进入 RL sanity。

如果这句话中的任一关键环节缺失，M2 不应直接标记为 PASS。
